# Точки входа: ?jobs, ?preflight, ?token, ?playlist, ?feedback

Сервер один - `index.php`, он же фронт-контроллер. Ниже - все его точки входа, кроме обычной отрисовки страницы.

## ?jobs

Фронтенд опрашивает снапшот `state/jobs.json` (см. ниже) каждые 1.5-12 секунд, а `index.php?jobs` - после действий. В ответ приходит JSON со всем, что нужно для перерисовки таблиц. Эндпоинт ничего не рендерит - только отдаёт данные.

## Запрос

```
GET /index.php?jobs
```

Ответ - `application/json`.

## Форма ответа

```json
{
  "jobs": [],
  "queue": [
    {
      "pid": "queueidXXXX",
      "url": "https://example.com/video",
      "dl_format": "Топ",
      "type": "video"
    }
  ],
  "finished": [],
  "videos": [],
  "music": [],
  "logURL": "",
  "proxy": {},
  "build": "a1b2c3d4e5f6"
}
```

| Поле | Тип | Что содержит |
|---|---|---|
| `jobs` | array | Активные (ещё идущие) загрузки - результат `Downloader::get_current_background_jobs()`. |
| `queue` | array | Загрузки, ожидающие своей очереди. Пустой массив, если `disableQueue` включён в конфиге. Каждый элемент - `pid`, `url`, `dl_format` (человекочитаемое название формата, например "Топ", "4K", "Булшит"), `type` (`video` или `audio`). |
| `finished` | array | Завершённые загрузки (успешные и с ошибкой) - результат `Downloader::get_finished_background_jobs()`, с кешированием разбора логов. |
| `videos` | array | Список видеофайлов из папки загрузок (`FileHandler::listMedia()`), с полями строки файла (см. ниже). |
| `music` | array | Список аудиофайлов оттуда же, той же формы. |
| `logURL` | string | Относительный путь к логам, если `logURL` в конфиге не пустой. Иначе пустая строка. |
| `proxy` | object | Статус живости SOCKS5-прокси - результат `ProxyStatus::payload()` (окна 1/5/15 минут). |
| `build` | string | Версия кода (`JobsSnapshot::buildId()`): хэш `static_version` и времени правки статики и шаблонов. Страница знает свою (`BUILD_ID`); разошлась - вкладка перезагружается сама, см. ниже. |

## Поля одной строки файла (videos / music)

Формируются методом `JobsSnapshot::fileRow()` (`class/JobsSnapshot.php`). Ключевые поля:

| Поле | Что содержит |
|---|---|
| `downloadurl` | Относительный путь к файлу - используется и как ссылка на скачивание, и как ключ строки для анимации появления новых файлов, и для QR-кода. |
| `kind` | `'video'` или `'audio'` - используется встроенным плеером, чтобы показать нужный тег (`<video>`/`<audio>`). |
| `size` | Человекочитаемый размер ("1.2 МБ") - то, что видно в таблице. |
| `size_bytes` | Тот же размер сырыми байтами. Нужен, чтобы посчитать суммарный объём пачки при массовом скачивании, не разбирая строку обратно в число. |

## Снапшот: GET /state/jobs.json

Тот же ответ без поля `now`, который воркер (`bin/worker.php`) кладёт в `/dev/shm/kachalka/jobs.json`. nginx отдаёт его как статику, без PHP. Плановый опрос фронта идёт сюда с `If-None-Match`, и неизменившийся список приходит ответом 304 без тела. Часы сервера фронт берёт из заголовка `Date`.

- `mtime` снапшота воркер держит строго растущим: nginx строит ETag из `mtime` и размера, а две записи за секунду одной длины иначе дали бы одинаковый ETag.
- Без перемен файл всё равно трогается раз в 10 секунд. Если `Date` минус `Last-Modified` больше 30 секунд, воркер считается мёртвым, и фронт идёт в `index.php?jobs`. Туда же он идёт при 404 и сразу после действия пользователя: `?jobs` будит воркер и ждёт его прохода, иначе таблица на секунду показала бы состояние до нажатия.

## Автообновление открытых вкладок

Вкладка, открытая до выкатки, сверяет `build` из каждого опроса со своим `BUILD_ID`. Разошлись - перезагружается сама:

- скрытая вкладка - сразу;
- видимая - когда человек 10 секунд ничего не делает и не открыты модалка, выбор качества или режим выделения;
- черновик поля ссылки сохраняется в `sessionStorage` и возвращается после перезагрузки; вкладку сайта (`#hash`) и прокрутку восстанавливает браузер;
- на одну и ту же версию второй раз не перезагружается: если страница и после этого старая (кэш по дороге), петли не будет.

В dev код смонтирован живым, и `build` меняется от одного `minify_js.sh` - открытая dev-вкладка подхватывает правку без ручного обновления. Выключить: `?noreload` в адресе.

## Свежий CSRF-токен: GET ?token

```
GET /index.php?token
```

Ответ: `{"token": "..."}`, `Cache-Control: no-store`. Сессии живут в контейнере и пропадают при его пересоздании, поэтому первое действие на старой вкладке получает 403. Фронт (`csrfFetch()`) в этом случае берёт свежий токен здесь и повторяет запрос один раз - без `alert` и перезагрузки. Чужая страница ответ не прочитает: CORS-заголовков нет.

## Дополнительный режим ?cron

Если к запросу добавить `&cron`, эндпоинт делает ту же работу, но не отдаёт JSON. Оставлен для совместимости: очередь двигает фоновый воркер, и отдельный крон для неё не нужен. При живом воркере `?jobs&cron` только будит его.

## Проверка ссылок до отправки: QUERY ?preflight

```
QUERY /index.php?preflight
Content-Type: application/json

{"urls": ["https://...", "https://..."]}
```

Пока человек вставляет ссылку, фронт (с паузой 400 мс после ввода) спрашивает, что сервер сделает с ней прямо сейчас, и пишет ответ строкой под полем. Ответ: `{"level": "error" | "info" | "", "message": "..."}`. Пустое сообщение значит, что всё стартует сразу.

Сообщает то, чего фронт сам не знает:
- **error** - полный диск, больше 50 ссылок, ссылка, которую сервер не примет (внутренний адрес, чужая схема);
- **info** - сколько стартует сразу, а сколько встанет в очередь, пауза между стартами YouTube, недавний отказ хоста (429).

Ответ строится не отдельной копией правил, а холостым прогоном самой отправки (`new Downloader($list, dryRun: true)`): те же проверки и та же раскладка по хостам, слотам и интервалам, только без запуска и без записи в очередь.

Метод QUERY (RFC 10008) - безопасный запрос с телом. GET со списком ссылок в строке запроса упёрся бы в длину URL и осел бы в логах, а POST означал бы действие. Сессия и CSRF-токен не нужны: состояние не меняется, а чужая страница без CORS-preflight такой запрос не отправит и ответ не прочитает.

| Код | Когда |
|---|---|
| 200 | Ответ выше. Заголовок `Accept-Query: application/json`. |
| 400 | Тело не разбирается или в нём нет массива `urls`. |
| 413 | Тело больше 64 КБ. |
| 415 | `Content-Type` не `application/json`. |

Хостовый nginx обязан пропускать метод QUERY (`ops/host-nginx/.../kachalka`), иначе он отвечает 405, а общий `error_page` превращает это в 404. Фронт такой ответ молча игнорирует, но 404 на каждый набор ссылки в поле видит fail2ban.

## Разбор плейлиста: POST playlist, GET ?playlist

Две половины одной операции. Разбор запускается **только POST-ом** и требует CSRF-токен: он поднимает процесс и ходит в сеть от имени пользователя, а GET, дёргающий внешнюю выборку, - это усилитель CSRF. Чтение состояния идёт GET-ом по непрозрачному ключу, который сервер сам и выдал.

```
POST /index.php        playlist=<url>   → {"state":"pending","key":"..."}
GET  /index.php?playlist=<ключ>         → состояние
```

Разбор асинхронный не по вкусу, а по необходимости: `--flat-playlist -J` по SOCKS5 на большом списке идёт десятками секунд, а nginx обрывает ответ PHP на 30 секундах. Процесс поднимается в фоне, браузер опрашивает состояние раз в 1.2 секунды.

| `state` | Что значит |
|---|---|
| `pending` | Разбор идёт, приходи позже. |
| `ready` | Готово, в ответе содержимое списка. |
| `error` | Не вышло, в поле `error` - текст для человека. |
| `missing` | Ключа нет: результат протух или его никогда не было. |

Ответ `ready` содержит:

| Поле | Что содержит |
|---|---|
| `contentType` | `playlist`, `multi_video` или `video` - ответ самого yt-dlp (`_type`). При `video` окно выбора не показывается вовсе, отправка идёт как обычно. |
| `title` | Название списка. |
| `count` | Сколько строк реально показывается, то есть длина `entries`. |
| `total` | Сколько роликов в списке на самом деле (`playlist_count` от yt-dlp). |
| `hidden` | Сколько записей отброшено: недоступные, повторы и пустышки на месте удалённых роликов. |
| `truncated` | `true`, если до нас доехал не весь список: упёрлись в потолок разбора (300 записей) либо yt-dlp насчитал больше, чем прислал. Скрытые строки сюда не входят. |
| `entries` | Массив: `id`, `url`, `title` (сырой текст, экранирует фронт), `duration`, `position`, `available`, `reason`. |

`position` - номер ролика в исходном плейлисте, считанный **до** отбрасывания. Нумеровать строки их порядком в `entries` нельзя: каждая отброшенная запись сдвигала бы номера, и выбранный "38-й" оказывался бы 43-м.

Недоступные записи в `entries` не попадают вовсе (`available` всегда `true`, поле оставлено для совместимости): выбрать такую строку было нельзя, а место и внимание она занимала. Повторы одного ролика отброшены по `id` - в YouTube Mix они обычное дело.

Ограничители: не больше 5 запусков в минуту с адреса, не больше 3 разборов одновременно, отказ при живом кулдауне хоста и при мёртвом прокси. Результат кешируется на 10 минут, повторный запрос того же плейлиста отвечает мгновенно.

Ссылки в `entries` собирает сервер - фронт их не конструирует, чтобы правила сборки не разъехались между двумя реализациями.

## Страница обратной связи: ?feedback

```
GET  /index.php?feedback            список обращений (плюс &page=N)
GET  /index.php?feedback=<id>       один диалог
POST feedback_new / feedback_reply / feedback_delete_message / feedback_delete_dialog
```

Не API: ветка рисует HTML (`views/part.feedback.php` вместо главной страницы), POST отвечает редиректом. Форма обычная и работает без JavaScript, поэтому результат едет через сессию, а не через JSON. Все четыре POST-ключа требуют CSRF-токен. Выключено в конфиге - страница отдаёт 404, POST закрыт.
