# Точки входа: ?jobs, ?playlist, ?feedback

Сервер один - `index.php`, он же фронт-контроллер. Ниже - все его точки входа, кроме обычной отрисовки страницы.

## ?jobs

Фронтенд опрашивает `index.php?jobs` каждые 1.5-12 секунд и получает JSON со всем, что нужно для перерисовки таблиц. Эндпоинт ничего не рендерит - только отдаёт данные.

## Запрос

```
GET /index.php?jobs
```

Ответ - `application/json`.

## Форма ответа

```json
{
  "jobs": [],
  "queue": [
    {
      "pid": "queueidXXXX",
      "url": "https://example.com/video",
      "dl_format": "Топ",
      "type": "video"
    }
  ],
  "finished": [],
  "videos": [],
  "music": [],
  "logURL": "",
  "proxy": {}
}
```

| Поле | Тип | Что содержит |
|---|---|---|
| `jobs` | array | Активные (ещё идущие) загрузки - результат `Downloader::get_current_background_jobs()`. |
| `queue` | array | Загрузки, ожидающие своей очереди. Пустой массив, если `disableQueue` включён в конфиге. Каждый элемент - `pid`, `url`, `dl_format` (человекочитаемое название формата, например "Топ", "4K", "Булшит"), `type` (`video` или `audio`). |
| `finished` | array | Завершённые загрузки (успешные и с ошибкой) - результат `Downloader::get_finished_background_jobs()`, с кешированием разбора логов. |
| `videos` | array | Список видеофайлов из папки загрузок (`FileHandler::listMedia()`), с полями строки файла (см. ниже). |
| `music` | array | Список аудиофайлов оттуда же, той же формы. |
| `logURL` | string | Относительный путь к логам, если `logURL` в конфиге не пустой. Иначе пустая строка. |
| `proxy` | object | Статус живости SOCKS5-прокси - результат `ProxyStatus::payload()` (окна 1/5/15 минут). |

## Поля одной строки файла (videos / music)

Формируются функцией `generateFileRow()` в `index.php`. Ключевые поля:

| Поле | Что содержит |
|---|---|
| `downloadurl` | Относительный путь к файлу - используется и как ссылка на скачивание, и как ключ строки для анимации появления новых файлов, и для QR-кода. |
| `kind` | `'video'` или `'audio'` - используется встроенным плеером, чтобы показать нужный тег (`<video>`/`<audio>`). |
| `size` | Человекочитаемый размер ("1.2 МБ") - то, что видно в таблице. |
| `size_bytes` | Тот же размер сырыми байтами. Нужен, чтобы посчитать суммарный объём пачки при массовом скачивании, не разбирая строку обратно в число. |

## Дополнительный режим ?cron

Если к запросу добавить `&cron`, эндпоинт всё так же продвигает очередь загрузок (`process_queue()`), но не отдаёт JSON и не завершает вывод с `Content-Type: application/json` - используется, чтобы гарантированно двигать очередь по расписанию, даже если никто не смотрит на страницу.

## Разбор плейлиста: POST playlist, GET ?playlist

Две половины одной операции. Разбор запускается **только POST-ом** и требует CSRF-токен: он поднимает процесс и ходит в сеть от имени пользователя, а GET, дёргающий внешнюю выборку, - это усилитель CSRF. Чтение состояния идёт GET-ом по непрозрачному ключу, который сервер сам и выдал.

```
POST /index.php        playlist=<url>   → {"state":"pending","key":"..."}
GET  /index.php?playlist=<ключ>         → состояние
```

Разбор асинхронный не по вкусу, а по необходимости: `--flat-playlist -J` по SOCKS5 на большом списке идёт десятками секунд, а nginx обрывает ответ PHP на 30 секундах. Процесс поднимается в фоне, браузер опрашивает состояние раз в 1.2 секунды.

| `state` | Что значит |
|---|---|
| `pending` | Разбор идёт, приходи позже. |
| `ready` | Готово, в ответе содержимое списка. |
| `error` | Не вышло, в поле `error` - текст для человека. |
| `missing` | Ключа нет: результат протух или его никогда не было. |

Ответ `ready` содержит:

| Поле | Что содержит |
|---|---|
| `contentType` | `playlist`, `multi_video` или `video` - ответ самого yt-dlp (`_type`). При `video` окно выбора не показывается вовсе, отправка идёт как обычно. |
| `title` | Название списка. |
| `count` | Сколько строк реально показывается, то есть длина `entries`. |
| `total` | Сколько роликов в списке на самом деле (`playlist_count` от yt-dlp). |
| `hidden` | Сколько записей отброшено: недоступные, повторы и пустышки на месте удалённых роликов. |
| `truncated` | `true`, если до нас доехал не весь список: упёрлись в потолок разбора (300 записей) либо yt-dlp насчитал больше, чем прислал. Скрытые строки сюда не входят. |
| `entries` | Массив: `id`, `url`, `title` (сырой текст, экранирует фронт), `duration`, `position`, `available`, `reason`. |

`position` - номер ролика в исходном плейлисте, считанный **до** отбрасывания. Нумеровать строки их порядком в `entries` нельзя: каждая отброшенная запись сдвигала бы номера, и выбранный "38-й" оказывался бы 43-м.

Недоступные записи в `entries` не попадают вовсе (`available` всегда `true`, поле оставлено для совместимости): выбрать такую строку было нельзя, а место и внимание она занимала. Повторы одного ролика отброшены по `id` - в YouTube Mix они обычное дело.

Ограничители: не больше 5 запусков в минуту с адреса, не больше 3 разборов одновременно, отказ при живом кулдауне хоста и при мёртвом прокси. Результат кешируется на 10 минут, повторный запрос того же плейлиста отвечает мгновенно.

Ссылки в `entries` собирает сервер - фронт их не конструирует, чтобы правила сборки не разъехались между двумя реализациями.

## Страница обратной связи: ?feedback

```
GET  /index.php?feedback            список обращений (плюс &page=N)
GET  /index.php?feedback=<id>       один диалог
POST feedback_new / feedback_reply / feedback_delete_message / feedback_delete_dialog
```

Не API: ветка рисует HTML (`views/part.feedback.php` вместо главной страницы), POST отвечает редиректом. Форма обычная и работает без JavaScript, поэтому результат едет через сессию, а не через JSON. Все четыре POST-ключа требуют CSRF-токен. Выключено в конфиге - страница отдаёт 404, POST закрыт.
