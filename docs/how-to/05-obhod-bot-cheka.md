# Починить обход бот-чека YouTube

YouTube иногда требует "доказательство", что запрос идёт от живого человека, а не от скрипта. Без такого доказательства (PO-токена) yt-dlp получает ошибку `HTTP 429` или `Sign in to confirm you're not a bot`, и скачивание не идёт - особенно часто это случается через прокси с уже засвеченным IP.

Качалка обходит это локальным генератором токенов (`bgutil`) - без кук и без аккаунта Google. Обычно это работает незаметно, но иногда ломается, потому что YouTube время от времени меняет правила игры.

## Симптом

В списке загрузок появляется ошибка "YouTube принял нас за бота" - при том, что ещё вчера всё работало.

## Проверить, жив ли сервер токенов

```bash
docker exec yt sh -c 'curl -s 127.0.0.1:4416/ping; echo; tail /var/www/YT/tmp/bgutil.log'
```

Ответ `/ping` должен содержать JSON с версией сервиса. Если ответа нет вообще - сервер токенов внутри контейнера умер (он запускается без авто-рестарта) и его не воскресит ничего, кроме пересборки или перезапуска контейнера.

## Проверить, что плагин загружается

```bash
docker exec yt /.yt_env/bin/yt-dlp --plugin-dirs default -v --simulate 'https://youtu.be/<id>' 2>&1 | grep -i pot
```

Если строк про `pot` нет вообще - значит плагин не подхватился yt-dlp'ом.

## Починить

В большинстве случаев помогает пересборка образа - она подтягивает актуальные версии сразу и плагина, и сервера токенов:

```bash
docker build --no-cache -t yt . && docker-compose up -d
```

## Подключить куки аккаунта (запасной путь)

`bgutil` снимает бот-чек без всякого входа в аккаунт, и в обычной ситуации этого достаточно. Но он не открывает контент, для которого нужен вход: приватные видео, возрастные ограничения, ролики только для подписчиков. А ещё он иногда временно ломается (см. выше). На эти случаи можно подложить настоящие куки залогиненного аккаунта - тогда yt-dlp скачивает так, будто ты открыл ролик в браузере.

Это опция, а не замена `bgutil`. Куки **не** подключаются к каждой загрузке (это только сыпало бы лишние запросы и предупреждения в лог). Первая попытка всегда идёт как обычно, без кук, и только если она падает на бот-чеке, приватности, возрасте или подписке - Качалка сама повторяет ту же загрузку с куками. Пока идёт повтор, во вкладке "Загрузки" видно строку `Обычный способ заблокирован, пробую с куками аккаунта`, а успешный результат помечается в списке значком 🍪.

### Как настроить

1. Заведи **отдельный одноразовый Google-аккаунт**, не личный. Куки на сервере - это, по сути, доступ ко всему аккаунту; если сервер скомпрометируют, потеряется только этот аккаунт.
2. Экспортируй куки правильно, иначе они протухнут почти сразу:
   - открой **приватное окно** браузера и зайди под этим аккаунтом на youtube.com;
   - открой **любую другую вкладку** и закрой вкладку с youtube.com;
   - только теперь экспортируй куки расширением вида "Get cookies.txt LOCALLY" (формат Netscape, файл `cookies.txt`);
   - закрой приватное окно и больше не заходи в нём на youtube.com.

   Смысл: пока вкладка с youtube.com открыта в браузере, YouTube постоянно обновляет (ротирует) куки на лету. Если экспортировать их прямо из открытой вкладки, на сервер попадёт кука, которая вот-вот сама себя заменит - и по факту она уже почти мёртвая. Закрытая вкладка в приватном окне такой ротации не подвергается.
3. Положи файл на сервер, в каталог `app/var/www/YT/config/youtube_cookies.txt` (каталог `config` уже закрыт nginx). Этот путь смонтирован в контейнер как bind-mount (см. `docker-compose.yml`) - файл специально не запекается в образ через `Dockerfile`, чтобы обновление кук подхватывалось сразу, без пересборки:
   ```bash
   cp cookies.txt /path/to/repo/app/var/www/YT/config/youtube_cookies.txt
   chown www-data:www-data /path/to/repo/app/var/www/YT/config/youtube_cookies.txt
   chmod 600 /path/to/repo/app/var/www/YT/config/youtube_cookies.txt
   ```
   Права `600` (или `400`) важны: куки - это доступ ко всему аккаунту, и файл, читаемый группой/остальными, - утечка на мультиюзерном хосте. **Выставлять права и владельца нужно на хосте, при каждой замене файла**: через bind-mount владелец файла - хостовый UID, и подправить неверные права изнутри контейнера нельзя.
4. Путь уже прописан в `config.php` по умолчанию - если файла нет, куки просто не используются:
   ```php
   'youtubeCookiesFile' => '/var/www/YT/config/youtube_cookies.txt'
   ```
5. Файл уже в `.gitignore` - в репозиторий не попадёт.

### Когда куки протухнут

Реалистично куки живут **3-5 дней**, и это не косяк настройки - YouTube в последнее время специально режет им жизнь всем подряд, даже при правильном экспорте. Плюс аккаунт заходит только с серверного IP, а не из обычного браузера - для Google это тоже подозрительно и укорачивает срок жизни ещё сильнее.

Автоматически продлить куки на сервере нельзя - безопасного способа не существует. Единственное лекарство - вручную повторить экспорт: зайти под тем же аккаунтом (по инструкции выше, через закрытую вкладку в приватном окне) и заменить `cookies.txt` на сервере. Признак, что пора: в списке загрузок появляется `Куки YouTube протухли`.

Важно: куки снимают бот-чек и открывают закрытый контент, но **не** лечат рейт-лимит по IP. Если `429` лезет уже на первом запросе страницы - дело в репутации прокси-IP, и никакие куки не помогут (см. ниже).

## Куки для Instagram

Instagram - отдельный случай: там нет аналога `bgutil`, и многий контент (приватные аккаунты, stories, иногда обычные посты) вообще не отдаётся без входа в аккаунт. Поэтому в отличие от YouTube куки Instagram подключаются не повтором после ошибки, а сразу, с первой попытки - если файл настроен и пригоден для использования.

### Как настроить

1. Заведи **отдельный аккаунт Instagram**, не личный - по той же причине, что и с YouTube: куки на сервере равны доступу ко всему аккаунту.
2. Зайди под ним на instagram.com в браузере и экспортируй куки тем же расширением ("Get cookies.txt LOCALLY", формат Netscape).
3. Положи файл на сервер, в каталог `app/var/www/YT/config/instagram_cookies.txt`. Как и с YouTube, это отдельный bind-mount (см. `docker-compose.yml`), не запечённый в образ:
   ```bash
   cp cookies.txt /path/to/repo/app/var/www/YT/config/instagram_cookies.txt
   chown www-data:www-data /path/to/repo/app/var/www/YT/config/instagram_cookies.txt
   chmod 600 /path/to/repo/app/var/www/YT/config/instagram_cookies.txt
   ```
   Права `600` важны по тем же причинам, что и для YouTube (см. выше) - и так же выставлять их надо на хосте, при каждой замене файла, а не полагаться на self-heal внутри контейнера.
4. Путь уже прописан в `config.php` по умолчанию:
   ```php
   'instagramCookiesFile' => '/var/www/YT/config/instagram_cookies.txt'
   ```
   Если файла по этому пути нет или права неверные - Качалка просто скачивает без кук (сработает только для публичного контента), без ошибки.
5. Файл уже в `.gitignore` - в репозиторий не попадёт.

### Когда куки протухнут

Так же, как и с YouTube: признак - `Куки Instagram протухли` в списке загрузок. Лечится перезаходом под тем же аккаунтом и повторным экспортом `cookies.txt`.

## Если не помогло

Значит YouTube поменял внутреннюю защиту (BotGuard) сильнее, чем обычно, и нужно подождать, пока разработчики `bgutil` выпустят исправление, а после - пересобрать образ ещё раз.

Отдельно стоит проверить репутацию самого IP-адреса прокси: если ошибка `429` вылезает уже на первом же запросе страницы, это не бот-чек, а обычный рейт-лимит по IP, который никаким обходом не лечится - см. [раздел про бан IP](../explanation/06-youtube-i-perevod-kak-eto-rabotaet.md#что-влияет-на-скорость-бана-ip).

Как всё это устроено внутри - в [Как устроены перевод и обход бот-чека YouTube](../explanation/06-youtube-i-perevod-kak-eto-rabotaet.md).
