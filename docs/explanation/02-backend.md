# Backend: разбор кода

Backend написан на чистом PHP, без фреймворков. Весь код сосредоточен в нескольких файлах: точка входа `index.php` и три класса в папке `class/`.

## index.php - точка входа

Этот файл обрабатывает каждый запрос к сайту. Внутри он делает несколько вещей по очереди.

**Настройка сессии и заголовков.** Перед стартом сессии файл настраивает cookie (httponly, samesite, secure при HTTPS) и выставляет заголовки безопасности. Подробный разбор - в [Безопасности](05-bezopasnost.md).

**Проверка CSRF.** Две функции, `generateCsrfToken()` и `validateCsrfToken()`, защищают от подделки запросов. Токен генерируется один раз на сессию и сверяется при каждом действии, которое что-то меняет (запуск загрузки, удаление файла, остановка процесса).

**Отдача статуса (`?jobs`).** Если в запросе есть параметр `jobs`, сайт не рисует страницу, а просто отдаёт JSON со всем, что нужно фронтенду: список активных загрузок, очередь, завершённые загрузки и списки файлов (видео и музыка). Именно этот эндпоинт JavaScript дёргает каждые 1.5-12 секунд. Точная форма ответа - в [Формате ответа ?jobs](../reference/02-api-jobs-endpoint.md).

**Обработка действий (POST).** Дальше идёт блок, который смотрит, что пришло в POST-запросе:

| Параметр | Что делает |
|---|---|
| `urls` | Запустить новую загрузку. Перед этим проверяется, что на диске есть минимум 100 МБ - иначе yt-dlp упал бы с "No space left on device" уже в процессе. |
| `kill` | Остановить одну или все (`kill=all`) загрузки. |
| `delete` | Удалить готовый файл с диска. |
| `clearDownloads` | Кнопка "Очистить всё": массово удалить файлы категории (видео/музыка). Не путать с `clear`. |
| `pin` | Закрепить/открепить файл (см. [Закрепление файлов](../explanation/04-ochered-i-fishki.md#закрепление-файлов-пин)). |
| `clear` | Почистить историю (`recent`), очередь (`queue`) или одну запись - логи задач, не файлы. |
| `restart` | Перезапустить отменённую или завершённую загрузку той же командой. |
| `removeQueued` | Убрать задачу из очереди, пока она там ждёт. |
| `reorderQueue` | Переставить задачу в очереди на позицию вверх или вниз. |

Все действия, кроме `urls`, объединены в проверку `$isDestructive`: раз запрос что-то меняет - сначала CSRF-токен, при несовпадении страница ошибки из `error_pages.php`. У `urls` свой такой же обязательный `validateCsrfToken()` перед созданием `Downloader`.

Все действия, кроме `urls`, отвечают JSON без перезагрузки страницы - на фронте клик бьёт `fetch`-запросом (`submitActionFetch()`/`confirmAction()`), и обновлённое состояние подхватывается обычным опросом `?jobs`. Иначе каждый "Стоп" сбрасывал бы прокрутку и мигал вёрсткой. Только отправка новой ссылки (`urls`) - обычный POST формы с редиректом на вкладку из `redirectAfterSubmit`.

**Доверие к IP клиента.** Перед запуском загрузки `index.php` определяет настоящий IP пользователя. Заголовки `X-Forwarded-For` и `X-Real-IP` подделать может кто угодно, поэтому им доверяют только если запрос пришёл с приватного адреса (то есть точно через свой nginx или докер-сеть, а не прямо из интернета). Иначе используется `REMOTE_ADDR` - тот адрес, который видит сам сервер.

## class/Downloader.php - главный класс

Это самый большой и важный файл. Он отвечает за всё: запуск yt-dlp, чтение статусов, разбор ошибок, очередь, остановку процессов.

### Список доменов прямого доступа

В начале файла объявлен список `DIRECT_ACCESS_DOMAINS` - российские и не заблокированные сайты (vk.com, rutube.ru, ok.ru, телеканалы, Яндекс и так далее). Загрузки с этих доменов идут напрямую, без прокси - потому что иностранные прокси часто либо блокируются такими сервисами, либо просто работают нестабильно. Все остальные сайты (включая YouTube) идут через SOCKS5-прокси, если он настроен.

### Конструктор

При создании объекта `Downloader` с непустым списком ссылок он:
1. Проверяет, что папка для загрузок существует и доступна для записи.
2. Разбивает ввод через `splitUrls()` (так можно скачать сразу несколько видео одной отправкой формы) и проверяет каждую ссылку через `filter_var(..., FILTER_VALIDATE_URL)`, дополнительно пропуская только схемы `http` и `https`. Разделителем считается `||` или пробельный символ, **за которым сразу начинается новая ссылка** (`\s+(?=https?://)`): резать по любому пробелу нельзя, иначе ссылка с незакодированным пробелом внутри развалилась бы на валидный огрызок, который ушёл бы качаться не туда, и мусорный хвост. Запятая разделителем не считается - она легальна в пути и query.
3. Если все ссылки валидны - запускает `do_download()`.

### do_download(), addOneDownload() и dispatchGroup()

`do_download()` сначала один раз проверяет, что значение `max_dl` в конфиге вообще осмысленно (не 0 и не отрицательное, кроме особого `-1`), и передаёт весь список ссылок в `addOneDownload()`.

`addOneDownload()` разбивает ссылки на группы: сначала по хосту (разные сайты - разные группы), а несколько ссылок одного хоста дополнительно делятся на первую (без паузы) и остальные (отдельным процессом, с паузами между запросами - подробнее в [Как устроены перевод и обход бот-чека YouTube](06-youtube-i-perevod-kak-eto-rabotaet.md#3-плейлист-против-пачки-ссылок)). Каждая такая группа-хост уходит в `dispatchGroup()` отдельно.

Гейт `max_dl` живёт именно в `dispatchGroup()`: каждая группа-хост отдельно сверяется с числом уже запущенных процессов (`background_jobs()` видит и процессы, запущенные более ранними группами того же запроса), поэтому отправка с несколькими хостами не обходит лимит. `-1` запускает без ограничений, свободный слот запускает сразу, иначе группа встаёт в очередь (или получает ошибку при `disableQueue=true`). Про влияние на бан по IP - в [Как устроены перевод и обход бот-чека YouTube](06-youtube-i-perevod-kak-eto-rabotaet.md#2-параллельность-работает-внутри-лимита-не-в-обход-него).

### executeDownload() - сборка команды yt-dlp

Здесь собирается итоговая команда, которая запустится в shell. По шагам:

- Базовый бинарник из конфига плюс `--js-runtimes node` (см. [Архитектуру](01-arhitektura.md)).
- Подключение Python-плагина логирования через `--plugin-dirs` и `--use-postprocessor`.
- Шаблон имени файла и `--restrict-filenames`.
- Выбор качества. Если выбран "Булшит" (worst) - просто `-f worst`. Иначе видео качается до потолка `maxVideoRes` из конфига, а если пользователь зажал кнопку "Скачать" и выбрал явное качество (4K, 2K, 1080p) - это качество перекрывает потолок из настроек.
- Для YouTube добавляется `--sponsorblock-remove sponsor` - спонсорские вставки вырезаются из файла ещё на сервере.
- Скачивание идёт одним соединением на файл - почему не параллельными фрагментами, разобрано в [Очереди и других технических решениях](04-ochered-i-fishki.md#параллельные-фрагменты-убраны).
- Если выбрана конвертация в аудио - добавляется `-x` и формат (mp3, wav, aac, flac). Для видео вместо этого добавляется `--merge-output-format mp4`/`--remux-video mp4` и ключ фрагментированного mp4 для трансляций (см. [ниже](#трансляции-прогресс-записи-и-спасение-оборванного-файла)).
- Каждый параметр, который приходит от пользователя (URL, прокси, путь), оборачивается в `escapeshellarg()` - это защита от command injection, подробнее в [Безопасности](05-bezopasnost.md).
- Команда запускается через `exec()` с перенаправлением вывода в файл и сохранением PID процесса (`echo $! > pid-файл`), чтобы потом можно было найти и остановить именно этот процесс.

### scanLogPath() - один проход по tmp/ на весь запрос

`index.php` один раз в начале запроса вызывает `Downloader::scanLogPath()`, которая за один проход раскладывает файлы каталога по префиксам (`pid_*`/`ytdl_*`), и передаёт результат `$fileList` в `process_queue()`, `get_current_background_jobs()` и `get_finished_background_jobs()` - вместо трёх отдельных сканов каталога на каждый опрос `?jobs`. Каждый метод умеет сканировать и сам, если `$fileList` не передан.

### get_current_background_jobs() и get_finished_background_jobs()

Это пара методов, которые читают файлы из `tmp/` и превращают их в массив данных для фронтенда.

`get_current_background_jobs()` идёт по всем файлам `pid_*`, проверяет, жив ли ещё процесс (через `/proc/$pid`), и если жив - читает соответствующий лог-файл yt-dlp и вытаскивает из него текущий статус (название файла, на каком сайте, процент загрузки). Если процесс уже умер - лог переименовывается в `ytdl_*` (считается завершённым), а команда дополнительно проверяется, что это точно процесс yt-dlp (через чтение `/proc/$pid/cmdline`), а не случайно совпавший PID от другого процесса.

Очень длинные логи (долгий плейлист, перевод озвучки) не разбираются целиком: лог длиннее 64 КБ читается только головой (первые ~4 КБ, где печатаются имя сайта и заголовок плейлиста) и хвостом (последние 64 КБ - всё, что важно "сейчас"). Короткие логи, то есть подавляющее большинство загрузок, читаются целиком.

`get_finished_background_jobs()` делает похожее для завершённых логов (`ytdl_*`); если в логе не нашлось имя файла - что-то пошло не так, и запускается `parseYtDlpError()`. Разбор кешируется: сначала считается лёгкая сигнатура (имя + mtime + размер каждого `ytdl_*`-файла), и пока она не изменилась, отдаётся готовый результат из `tmp/.finished_cache` без открытия логов - кеш инвалидируется сам при появлении или дозаписи лога. Список отсортирован по времени изменения, свежие сверху.

### Трансляции: прогресс записи и спасение оборванного файла

Живой поток (Twitch и любой другой live-HLS) yt-dlp качает не сам, а через ffmpeg, и это ломало сразу две вещи.

Первая - статус. У трансляции нет ни общего размера, ни конца, поэтому процентов yt-dlp не печатает вовсе, и в интерфейсе намертво висело "Собираю информацию по сайту", хотя файл на диске рос. Теперь `scanForCurrentStatus()` ловит собственный прогресс ffmpeg (`size=`, `time=`, `bitrate=` и `speed=` в его строках) и показывает человеку "Записываю трансляцию: 512.3 МБ, 00:14:22, 1.1 МБ/с". Строки ffmpeg разделены не переводом строки, а `\r`, то есть весь прогресс приходит одной длинной строкой - поэтому ищутся все совпадения, а берётся последнее.

Скорость считается как битрейт потока, умноженный на `speed` - это коэффициент опережения реального времени. У ровно идущей трансляции он около 1.00x, и тогда скорость приёма просто равна битрейту, но в начале yt-dlp догоняет накопленный буфер и качает в несколько раз быстрее; без множителя в такие моменты показывалась бы заниженная цифра. Если ffmpeg почему-то не напечатал битрейт, скорость не показывается вовсе - размер и время остаются. Этот статус перекрывает общие "Собираю информацию"/"В Процессе", но уступает фазам перевода озвучки: там ffmpeg занят склейкой дорожек, а не приёмом потока.

Вторая - сам файл. Обычный mp4 хранит индекс (moov-атом) в конце, и он дописывается только при штатном завершении. Если трансляция оборвалась или человек нажал "Стоп", на диске оставался огрызок `имя.mp4.part`, который не открывался в принципе - ни плеером на странице, ни на компьютере. Лечится на этапе сборки команды: к видео-загрузкам добавлен `--downloader-args "ffmpeg:-movflags +frag_keyframe+empty_moov+default_base_moof"`. Фрагментированный mp4 пишет заголовки по ходу записи, поэтому проигрывается любой его обрезок. Голый префикс `ffmpeg:` yt-dlp подставляет в выходные аргументы ffmpeg, а когда качает не ffmpeg (обычное видео) - ключ просто не используется.

Осталось показать огрызок пользователю: `salvagePartialVideo()` снимает с него суффикс `.part`, после чего файл появляется во вкладке "Видео" как обычный. Вызывается она из `finalize_job_log()` - единственной точки, через которую проходит любое завершение задачи, будь то кнопка "Стоп", падение yt-dlp или обрыв самой трансляции.

Спасаются при этом только записи через ffmpeg - признаком служит его прогресс в логе. Прерванная обычная HTTP-загрузка даёт неполный нефрагментированный файл, который переименовывать нельзя: получился бы заведомо битый mp4 в списке готовых. Остальные проверки - белый список расширений (mp4, mkv, ts, webm), минимальный размер 256 КБ, отсутствие файла с целевым именем и проверка через `realpath()`, что путь не уводит за пределы папки загрузок. При штатном завершении `.part` переименовывает сам yt-dlp, так что делать здесь нечего.

### parseYtDlpError() - перевод ошибок на человеческий язык

Метод получает текст лога yt-dlp и ищет знакомые паттерны ошибок: не резолвится DNS, сайт вернул 403 или 404, видео приватное, требует авторизации, гео-блок, нет форматов для скачивания, не хватает места на диске и так далее. Правила заданы одной таблицей `ERROR_RULES` (пары "регулярное выражение - сообщение"), которая перебирается по порядку: первое совпадение выигрывает, поэтому порядок значим (сетевые ошибки идут раньше, чем ошибки контента). Полный список правил - в [Кодах ошибок yt-dlp](../reference/03-oshibki-yt-dlp.md). Добавить новую ошибку - просто вставить строку в таблицу.

Перед сравнением лог обязательно прогоняется через `sanitizeLog()` - это важно, потому что в логе могут быть IP-адреса, пароли от прокси или другие чувствительные данные, и показывать их пользователю нельзя.

### process_queue() - продвижение очереди

Очередь хранится в одном файле `dl_queue`, где каждая строка - это одна ожидающая загрузка. Метод открывает файл, ставит эксклюзивную блокировку (`LOCK_EX`), читает все строки, и для тех, на кого хватает места по лимиту `max_dl`, запускает реальную загрузку. Остальные строки остаются в файле. Блокировка нужна, чтобы два параллельных запроса (например, два человека одновременно открыли сайт) не испортили файл очереди друг другу.

### kill_one_of_them() и kill_them_all()

Останавливают один или все процессы yt-dlp. Важная деталь: перед тем как слать `kill`, метод проверяет через `/proc/$pid/cmdline`, что это действительно процесс yt-dlp, а не случайно совпавший по номеру чужой процесс на сервере. `kill_them_all()` ищет все процессы по имени (`pgrep -f 'yt-dlp'`) и завершает их, а также удаляет недокачанные `.part`-файлы, если в конфиге не включено `keepPartialFiles`. Записи трансляций до этой уборки не доживают: их `.part` уже переименован в нормальный файл (см. [Трансляции](#трансляции-прогресс-записи-и-спасение-оборванного-файла)).

Сигнал шлётся не одному PID, а всей его группе процессов (`kill -- -$pid`, а не `kill $pid`). Каждая загрузка запускается через `setsid`, что делает её лидером собственной группы - для обычной загрузки (один процесс) это ничего не меняет, но для задач с переводом озвучки (VOT, `bash -c "yt-dlp & ... vot-cli & ... wait"`) без этого сигнал долетал бы только до внешнего `bash`, а `yt-dlp`/`vot-cli`/`ffmpeg`-микс оставались бы жить осиротевшими и после нажатия "Стоп". Подробнее - в [Очереди и других технических решениях](04-ochered-i-fishki.md#остановка-перевода-озвучки-целиком-а-не-только-внешнего-процесса).

### restart_download()

Перезапускает старую загрузку, читая сохранённую команду прямо из лога. Здесь есть отдельная проверка безопасности: команда из лога сверяется с ожидаемым путём к `yt-dlp` - если не совпадает, рестарт отменяется, чтобы подменённый лог-файл не заставил сервер выполнить чужую команду. Опциональные `$forceUseProxy`/`$forceUseCookies` используются авторетреями (см. ниже).

### Два авторетрея: через прокси и через куки

Когда задача завершается с ошибкой, `get_current_background_jobs()` пробует два независимых механизма авто-перезапуска - сначала сетевой, потом кукисный:

| | Сетевой (`autoRetryIfNeeded`) | Кукисный (`autoRetryWithCookiesIfNeeded`) |
|---|---|---|
| Когда срабатывает | `isRetryableError()`: тайм-аут, 429, 503, DNS | `needsCookiesRetry()`: приватное видео, 18+, members-only, непробитый бот-чек |
| Что подключает | SOCKS5-прокси (`restart_download(..., $forceUseProxy)`) | Куки (`restart_download(..., $forceUseCookies)`) |
| Логика | Сайт блокирует прямые подключения, но пропускает через прокси | Ошибку чинит не сеть, а залогиненная сессия |

Общие правила для обоих: маркер `[RETRY_ATTEMPTED:]` в логе один на двоих - за жизнь задачи максимум одна авто-попытка; `canSpawnRetry()` следит, чтобы ретрей не пробивал лимит `max_dl`; для пользователя всё прозрачно - удался ретрей, видишь готовый файл, упали оба захода - финальную ошибку.

Кукисный ретрей дополнительно требует, чтобы куки были реально настроены и безопасны: `cookiesFileUsable()` проверяет, что файл существует, читается и не открыт группе/остальным (права чинятся до 0600 автоматически, если процесс - владелец). Если куки прописаны, но использовать их нельзя, `cookiesConfiguredButUnusable()` честно сообщает об этом в статусе задачи. Первая попытка всегда идёт без кук - публичный контент их вообще не видит. Как получить куки - в [Обходе бот-чека YouTube через куки](../how-to/05-obhod-bot-cheka.md).

## class/FileHandler.php - работа с файлами

Этот класс знает только про файлы на диске - он не запускает yt-dlp и не лезет в процессы.

- `listMedia()` - один проход `readdir()` по папке загрузок, который сразу возвращает и видео, и музыку (`['videos' => [...], 'musics' => [...]]`), каждый файл с возрастом в минутах и процентом "оставшегося времени жизни" (окно берётся из конфига `retentionMinutes`). Оба списка отсортированы по времени изменения, свежие сверху.
- `isPinned()`/`setPinned()` - закрепление файла ("пин") маркером `{имя}.keep` рядом с файлом, с тем же `realpath()`-предохранителем от выхода за пределы папки, что и у `delete()`. Закреплённый файл не участвует в возрастном отсчёте времени жизни - подробнее в [Закреплении файлов](04-ochered-i-fishki.md#закрепление-файлов-пин).
- `delete()` - удаляет один файл по имени. Здесь стоит защита от выхода за пределы папки: имя файла сначала чистится через `basename()` (убирает любые `../`), а затем через `realpath()` проверяется, что итоговый абсолютный путь действительно находится внутри разрешённой папки загрузок.
- `deleteAll()` - массовое удаление для кнопки "Очистить всё" (отдельно по видео/музыке или разом), с тем же `realpath()`-предохранителем; пропускает закреплённые файлы и, пока есть хоть одна работающая загрузка, файлы младше 60 секунд - подробнее в [Массовой очистке](04-ochered-i-fishki.md#массовая-очистка-отдельно-по-видео-и-музыке).
- `to_human_filesize()` - превращает байты в читаемый размер (КБ, МБ, ГБ).

## class/ProxyStatus.php - живость прокси

Небольшой класс, который отвечает за индикатор состояния SOCKS5-прокси в футере. Раз в минуту (`maybe_check()`, под неблокирующим flock, чтобы параллельные запросы не плодили процессы) он в фоне дёргает через прокси нейтральный `gstatic.com/generate_204` и дописывает в `tmp/proxy_probe.log` одну строку `timestamp 0|1`. По этой истории `get_windows()` строит три окна - 1, 5 и 15 минут - и отдаёт их в `?jobs`, откуда фронтенд красит точки в футере.

Сам прокси наружу не утекает: в лог идут только время и статус, строка прокси живёт лишь в окружении временного curl-процесса. Что видит пользователь и как читаются цвета - в [Очереди и других технических решениях](04-ochered-i-fishki.md#индикатор-живости-прокси-в-футере).

## error_pages.php

Содержит одну функцию `showCsrfErrorPage()` - красивую страницу с кодом 403, которая показывается, если проверка CSRF-токена не прошла (например, страница была открыта слишком давно и токен в сессии устарел). Её кнопки ("Обновить", "Назад") работают через небольшой nonce-скрипт, а не через inline `onclick` - чтобы страница вписывалась в общую CSP без `unsafe-inline`.
