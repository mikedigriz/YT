# Backend: разбор кода

Backend написан на чистом PHP, без фреймворков. Весь код сосредоточен в нескольких файлах: точка входа `index.php` и три класса в папке `class/`.

## index.php - точка входа

Этот файл обрабатывает каждый запрос к сайту. Внутри он делает несколько вещей по очереди.

**Настройка сессии и заголовков.** Перед стартом сессии файл настраивает cookie (httponly, samesite, secure при HTTPS) и выставляет заголовки безопасности. Подробный разбор - в [Безопасности](05-bezopasnost.md).

**Проверка CSRF.** Две функции, `generateCsrfToken()` и `validateCsrfToken()`, защищают от подделки запросов. Токен генерируется один раз на сессию и сверяется при каждом действии, которое что-то меняет (запуск загрузки, удаление файла, остановка процесса).

**Отдача статуса (`?jobs`).** Если в запросе есть параметр `jobs`, сайт не рисует страницу, а просто отдаёт JSON со всем, что нужно фронтенду: список активных загрузок, очередь, завершённые загрузки и списки файлов (видео и музыка). Именно этот эндпоинт JavaScript дёргает каждые 1.5-12 секунд. Точная форма ответа - в [Формате ответа ?jobs](../reference/02-api-jobs-endpoint.md).

**Обработка действий (POST).** Дальше идёт блок, который смотрит, что пришло в POST-запросе:

| Параметр | Что делает |
|---|---|
| `urls` | Запустить новую загрузку. Перед этим проверяется, что на диске есть минимум 100 МБ - иначе yt-dlp упал бы с "No space left on device" уже в процессе. |
| `kill` | Остановить одну или все (`kill=all`) загрузки. |
| `delete` | Удалить готовый файл с диска. |
| `clearDownloads` | Кнопка "Очистить всё": массово удалить файлы категории (видео/музыка). Не путать с `clear`. |
| `pin` | Закрепить/открепить файл (см. [Закрепление файлов](../explanation/04-ochered-i-fishki.md#закрепление-файлов-пин)). |
| `clear` | Почистить историю (`recent`), очередь (`queue`) или одну запись - логи задач, не файлы. |
| `restart` | Перезапустить отменённую или завершённую загрузку той же командой. |
| `removeQueued` | Убрать задачу из очереди, пока она там ждёт. |
| `reorderQueue` | Переставить задачу в очереди на позицию вверх или вниз. |
| `playlist` | Запустить разбор плейлиста. Поднимает процесс и ходит в сеть, поэтому только POST и только с токеном - GET, дёргающий внешнюю выборку, это усилитель CSRF. |
| `feedback_new`, `feedback_reply` | Новое обращение и ответ в существующее. |
| `feedback_delete_message`, `feedback_delete_dialog` | Удаление сообщения и всего обращения - только администратору. |

Все действия, кроме `urls`, объединены в проверку `$isDestructive`: раз запрос что-то меняет - сначала CSRF-токен, при несовпадении страница ошибки из `error_pages.php`. У `urls` свой такой же обязательный `validateCsrfToken()` перед созданием `Downloader`.

Отправка ссылок отвечает **JSON**, если запрос пришёл с заголовком `X-Requested-With: fetch` - его ставит фронтенд. В ответе видно, что запустилось, что встало в очередь, что отклонено и что вернуть в поле ввода. Без этого заголовка работает старый путь с редиректом на вкладку из `redirectAfterSubmit`, поэтому страница остаётся рабочей и с выключенным JavaScript.

Одна кривая ссылка больше не отменяет всю пачку: валидные уходят качаться, отклонённые возвращаются в поле - повторная отправка не задваивает уже запущенное.

Действия над задачами и файлами отвечают JSON без перезагрузки страницы: на фронте клик бьёт `fetch`-запросом, обновлённое состояние подхватывается обычным опросом `?jobs`. Иначе каждый "Стоп" сбрасывал бы прокрутку и мигал вёрсткой. Обратная связь устроена наоборот - обычная форма и редирект: она обязана работать без JavaScript целиком.

**Доверие к IP клиента.** `clientIp()` определяет настоящий адрес пользователя. Заголовки `X-Forwarded-For` и `X-Real-IP` подделать может кто угодно, поэтому им доверяют только если запрос пришёл с приватного адреса (то есть точно через свой nginx или докер-сеть, а не прямо из интернета). Иначе используется `REMOTE_ADDR` - тот адрес, который видит сам сервер.

Порядок чтения заголовков здесь не косметика. Сначала берётся `X-Real-IP`: прокси ставит его равным адресу соединения, то есть значение целиком его. Из `X-Forwarded-For` берётся **последний** элемент, а не первый - стандартный дебиановский `proxy_params` собирает этот заголовок дописыванием к клиентскому значению, и первым там лежит то, что прислал клиент. Пока адрес нужен был только лимитам частоты, ценой ошибки был обход лимита; с появлением доверенных сетей администратора доски обратной связи чтение первого элемента стало прямым обходом пароля. Требование к пограничному прокси - в [Поставить сайт за HTTPS](../how-to/06-reverse-proxy-https.md).

## class/Downloader.php - главный класс

Это самый большой и важный файл. Он отвечает за всё: запуск yt-dlp, чтение статусов, разбор ошибок, очередь, остановку процессов.

### Список доменов прямого доступа

В начале файла объявлен список `DIRECT_ACCESS_DOMAINS` - российские и не заблокированные сайты (vk.com, rutube.ru, ok.ru, телеканалы, Яндекс и так далее). Загрузки с этих доменов идут напрямую, без прокси - потому что иностранные прокси часто либо блокируются такими сервисами, либо просто работают нестабильно. Все остальные сайты (включая YouTube) идут через SOCKS5-прокси, если он настроен.

### Конструктор

При создании объекта `Downloader` с непустым списком ссылок он:
1. Проверяет, что папка для загрузок существует и доступна для записи.
2. Разбивает ввод через `splitUrls()` (так можно скачать сразу несколько видео одной отправкой формы) и проверяет каждую ссылку через `filter_var(..., FILTER_VALIDATE_URL)`, дополнительно пропуская только схемы `http` и `https`. Разделитель полей - `||`, а каждый кусок дополнительно прогоняется через `extractUrls()`: из вставленной переписки ссылки выдёргиваются, остальное выбрасывается. Правило осторожное - разбор прозы включается, только если ссылок две и больше или перед первой стоит мусор. Одна ссылка с хвостом после пробела возвращается целиком: отличить прозу от незакодированного пробела внутри адреса нечем, а обрезать было бы хуже - получился бы валидный адрес, ведущий не туда. Запятая разделителем не считается, она легальна в пути и query.
3. Если все ссылки валидны - запускает `do_download()`.

### do_download(), addOneDownload() и dispatchGroup()

`do_download()` сначала один раз проверяет, что значение `max_dl` в конфиге вообще осмысленно (не 0 и не отрицательное, кроме особого `-1`), и передаёт весь список ссылок в `addOneDownload()`.

`addOneDownload()` разбивает ссылки на группы: сначала по хосту (разные сайты - разные группы), а несколько ссылок одного хоста дополнительно делятся на первую (без паузы) и остальные (отдельным процессом, с паузами между запросами - подробнее в [Как устроены перевод и обход бот-чека YouTube](06-youtube-i-perevod-kak-eto-rabotaet.md#3-плейлист-против-пачки-ссылок)). Каждая такая группа-хост уходит в `dispatchGroup()` отдельно.

Гейт `max_dl` живёт именно в `dispatchGroup()`: каждая группа-хост отдельно сверяется с числом уже запущенных процессов (`background_jobs()` видит и процессы, запущенные более ранними группами того же запроса), поэтому отправка с несколькими хостами не обходит лимит. `-1` запускает без ограничений, свободный слот запускает сразу, иначе группа встаёт в очередь (или получает ошибку при `disableQueue=true`). Про влияние на бан по IP - в [Как устроены перевод и обход бот-чека YouTube](06-youtube-i-perevod-kak-eto-rabotaet.md#2-параллельность-работает-внутри-лимита-не-в-обход-него).

### executeDownload() - сборка команды yt-dlp

Здесь собирается итоговая команда, которая запустится в shell. По шагам:

- Базовый бинарник из конфига плюс `--js-runtimes node` (см. [Архитектуру](01-arhitektura.md)).
- Подключение Python-плагина логирования через `--plugin-dirs` и `--use-postprocessor`.
- Шаблон имени файла и `--restrict-filenames`.
- Выбор качества. Если выбран "Булшит" (worst) - просто `-f worst`. Иначе видео качается до потолка `maxVideoRes` из конфига, а если пользователь зажал кнопку "Скачать" и выбрал явное качество (4K, 2K, 1080p) - это качество перекрывает потолок из настроек.
- Для YouTube добавляется `--sponsorblock-remove sponsor` - спонсорские вставки вырезаются из файла ещё на сервере.
- Ускорение закачки, если оно разрешено обстановкой: `--downloader aria2c` на цельных файлах прямых доменов либо `--concurrent-fragments` на фрагментированном видео. Число соединений считается на старте задачи, а не берётся константой - разбор в [Очереди и других технических решениях](04-ochered-i-fishki.md#ускорение-закачки).
- Если выбрана конвертация в аудио - добавляется `-x` и формат (mp3, wav, aac, flac). Для видео вместо этого добавляется `--merge-output-format mp4`/`--remux-video mp4` и ключ фрагментированного mp4 для трансляций (см. [ниже](#трансляции-прогресс-записи-и-спасение-оборванного-файла)). У прямой ссылки на видеофайл (".../clip.webm") из этого набора остаётся один `--remux-video mp4`: сливать нечего, формат один, а ffmpeg файл не тянет.
- Любой видеозадаче добавляется `--exec after_move:/etc/Scripts/ensure_mp4.sh %(filepath)q`. Точка подключения именно `after_move:`, а не `after_video:` - у последней поле `%(filepath)q` ещё не заполнено, и скрипт получал вместо пути строку `NA`. Контейнер mp4 обеспечивает ремукс, но контейнера мало: VP9 и Opus кладутся в mp4 законно, а Safari, iOS и QuickTime такой файл не откроют. Скрипт смотрит `ffprobe`, что внутри, и перекодирует **только несовместимую дорожку** - в типичном случае (h264+aac) он стоит одного вызова `ffprobe` и ничего не трогает. Выключается ключом `mp4Compat`.
- Каждый параметр, который приходит от пользователя (URL, прокси, путь), оборачивается в `escapeshellarg()` - это защита от command injection, подробнее в [Безопасности](05-bezopasnost.md).
- Команда запускается через `exec()` с перенаправлением вывода в файл и сохранением PID процесса (`echo $! > pid-файл`), чтобы потом можно было найти и остановить именно этот процесс.

### scanLogPath() - один проход по tmp/ на весь запрос

`index.php` один раз в начале запроса вызывает `Downloader::scanLogPath()`, которая за один проход раскладывает файлы каталога по префиксам (`pid_*`/`ytdl_*`), и передаёт результат `$fileList` в `process_queue()`, `get_current_background_jobs()` и `get_finished_background_jobs()` - вместо трёх отдельных сканов каталога на каждый опрос `?jobs`. Каждый метод умеет сканировать и сам, если `$fileList` не передан.

### get_current_background_jobs() и get_finished_background_jobs()

Это пара методов, которые читают файлы из `tmp/` и превращают их в массив данных для фронтенда.

`get_current_background_jobs()` идёт по всем файлам `pid_*`, проверяет, жив ли ещё процесс (через `/proc/$pid`), и если жив - читает соответствующий лог-файл yt-dlp и вытаскивает из него текущий статус (название файла, на каком сайте, процент загрузки). Если процесс уже умер - лог переименовывается в `ytdl_*` (считается завершённым), а команда дополнительно проверяется, что это точно процесс yt-dlp (через чтение `/proc/$pid/cmdline`), а не случайно совпавший PID от другого процесса.

Очень длинные логи (долгий плейлист, перевод озвучки) не разбираются целиком: лог длиннее 64 КБ читается только головой (первые ~4 КБ, где печатаются имя сайта и заголовок плейлиста) и хвостом (последние 64 КБ - всё, что важно "сейчас"). Короткие логи, то есть подавляющее большинство загрузок, читаются целиком.

`get_finished_background_jobs()` делает похожее для завершённых логов (`ytdl_*`); если в логе не нашлось имя файла - что-то пошло не так, и запускается `parseYtDlpError()`. Разбор кешируется: сначала считается лёгкая сигнатура (имя + mtime + размер каждого `ytdl_*`-файла), и пока она не изменилась, отдаётся готовый результат из `tmp/.finished_cache` без открытия логов - кеш инвалидируется сам при появлении или дозаписи лога. Список отсортирован по времени изменения, свежие сверху.

### Трансляции: прогресс записи и спасение оборванного файла

Живой поток (Twitch и любой другой live-HLS) yt-dlp качает не сам, а через ffmpeg, и это ломало сразу две вещи.

Первая - статус. У трансляции нет ни общего размера, ни конца, поэтому процентов yt-dlp не печатает вовсе, и в интерфейсе намертво висело "Собираю информацию по сайту", хотя файл на диске рос. Теперь `scanForCurrentStatus()` ловит собственный прогресс ffmpeg (`size=`, `time=`, `bitrate=` и `speed=` в его строках) и показывает человеку "Записываю трансляцию: 512.3 МБ, 00:14:22, 1.1 МБ/с". Строки ffmpeg разделены не переводом строки, а `\r`, то есть весь прогресс приходит одной длинной строкой - поэтому ищутся все совпадения, а берётся последнее.

Скорость считается как битрейт потока, умноженный на `speed` - это коэффициент опережения реального времени. У ровно идущей трансляции он около 1.00x, и тогда скорость приёма просто равна битрейту, но в начале yt-dlp догоняет накопленный буфер и качает в несколько раз быстрее; без множителя в такие моменты показывалась бы заниженная цифра. Если ffmpeg почему-то не напечатал битрейт, скорость не показывается вовсе - размер и время остаются. Этот статус перекрывает общие "Собираю информацию"/"В Процессе", но уступает фазам перевода озвучки: там ffmpeg занят склейкой дорожек, а не приёмом потока.

Вторая - сам файл. Обычный mp4 хранит индекс (moov-атом) в конце, и он дописывается только при штатном завершении. Если трансляция оборвалась или человек нажал "Стоп", на диске оставался огрызок `имя.mp4.part`, который не открывался в принципе - ни плеером на странице, ни на компьютере. Лечится на этапе сборки команды: к видео-загрузкам добавлен `--downloader-args "ffmpeg:-movflags +frag_keyframe+empty_moov+default_base_moof"`. Фрагментированный mp4 пишет заголовки по ходу записи, поэтому проигрывается любой его обрезок. Голый префикс `ffmpeg:` yt-dlp подставляет в выходные аргументы ffmpeg, а когда качает не ffmpeg (обычное видео) - ключ просто не используется.

Осталось показать огрызок пользователю: `salvagePartialVideo()` снимает с него суффикс `.part`, после чего файл появляется во вкладке "Видео" как обычный. Вызывается она из `finalize_job_log()` - единственной точки, через которую проходит любое завершение задачи, будь то кнопка "Стоп", падение yt-dlp или обрыв самой трансляции.

Спасаются при этом только записи через ffmpeg - признаком служит его прогресс в логе. Прерванная обычная HTTP-загрузка даёт неполный нефрагментированный файл, который переименовывать нельзя: получился бы заведомо битый mp4 в списке готовых. Остальные проверки - белый список расширений (mp4, mkv, ts, webm), минимальный размер 256 КБ, отсутствие файла с целевым именем и проверка через `realpath()`, что путь не уводит за пределы папки загрузок. При штатном завершении `.part` переименовывает сам yt-dlp, так что делать здесь нечего.

### parseYtDlpError() - перевод ошибок на человеческий язык

Метод получает текст лога yt-dlp и ищет знакомые паттерны ошибок: не резолвится DNS, сайт вернул 403 или 404, видео приватное, требует авторизации, гео-блок, нет форматов для скачивания, не хватает места на диске и так далее. Правила заданы одной таблицей `ERROR_RULES` (пары "регулярное выражение - сообщение"), которая перебирается по порядку: первое совпадение выигрывает, поэтому порядок значим (сетевые ошибки идут раньше, чем ошибки контента). Полный список правил - в [Кодах ошибок yt-dlp](../reference/03-oshibki-yt-dlp.md). Добавить новую ошибку - просто вставить строку в таблицу.

Перед сравнением лог обязательно прогоняется через `sanitizeLog()` - это важно, потому что в логе могут быть IP-адреса, пароли от прокси или другие чувствительные данные, и показывать их пользователю нельзя.

### Пауза после 429

При завершении задачи лог проверяется на настоящий отказ хоста, и рядом с логами появляется отметка `cooldown_<хост>`; время её жизни - `hostCooldownMinutes`, а отсчёт идёт от времени изменения самого файла, отдельного поля не нужно.

"Настоящий отказ" - строка `ERROR:` с 429/`Too Many Requests` **и** задача не оставила итогового файла. `WARNING:` про 429 на странице сам по себе кулдаун не ставит: у YouTube это обычный первый шаг перед откатом на API, он есть почти в каждом здоровом логе, и без разбора отметка обновлялась бы на каждом завершении - очередь и проба плейлиста для youtube.com почти не выходили бы из кулдауна, пока задачи продолжают выполняться.

`process_queue()` задачи такого хоста **пропускает**, оставляя их в очереди, а слот отдаёт следующей задаче другого сайта. Строгий порядок очереди здесь нарушен сознательно: при `max_dl = 1` один придержанный сайт иначе остановил бы всю очередь. Разбор плейлиста для хоста в кулдауне тоже не запускается - незачем ходить туда, куда только что попросили не ходить.

### Ожидание анонсированного эфира

YouTube-задачи получают `--wait-for-video 30-300` (ключ `waitForVideo`): ссылку на будущий стрим можно поставить заранее, задача дождётся начала и запишет сама.

Такая задача **не считается** в `background_jobs()`, иначе при лимите в одну загрузку она заперла бы очередь на часы, ничего не качая. Отличить её от работающей помогает хвост лога: строка ожидания есть, а `Destination:` и строк загрузки ещё нет. Как только эфир начался, задача попадает в счёт со следующего опроса, а в интерфейсе вместо зависшего "Собираю информацию" пишется "Жду начала эфира, слот очереди не занимаю".

Обратная сторона ключа: `--wait-for-video` виснет не только на честном анонсе, но и на любой недоступности - возрастной гейт, бот-чек, приватный ролик. yt-dlp упорно ждёт "начала" того, что никогда не начнётся, а задача при этом даже не помечена неудачной, то есть авторетрей с куками не сработает никогда. Сторож `abortHopelessWaiters()` (зовётся на каждом опросе) читает хвост job-лога и гасит такую задачу: строк `Destination:`/`[download]` нет, зато признаки закрытого контента встретились минимум дважды. Двух совпадений требует не осторожность, а устройство yt-dlp: он перебирает клиентов (`--extractor-args player_client`), и первый может схватить бот-чек там, где следующий спокойно скачает ролик. Лог финализируется **без** суффикса `_cancelled` - "отменено" тут неправда, да и авторетреи отменённые логи пропускают, а нужен ровно повтор с куками.

### Проверка готового файла

yt-dlp умеет выйти с кодом 0 и оставить огрызок: сеть умерла на последних байтах, постпроцессор упал, диск кончился. Поэтому цели из `Destination:` прогоняются через `ffprobe` (он и так есть в образе вместе с ffmpeg), и если ни один файл не читается, в лог дописывается строка `ERROR:` - дальше её подхватывает разбор ошибок, и задача честно становится неудачной вместо "Готово" поверх битого файла.

Там же проверяется звук. Если в логе видно, что yt-dlp выбирал видео и аудио по отдельности (`Downloading 1 format(s): 137+140`), в итоговом файле обязана быть звуковая дорожка; её отсутствие - тот же `ERROR:` в лог и статус "Звук не докачался". Проверка узкая нарочно: у прямой ссылки на файл и у роликов без звука формат один, `+` в логе не появляется, и немой превью со стока браком не считается.

Три оговорки. Записи через ffmpeg судятся по одному декодируемому кадру, а не по длительности: у спасённого огрызка трансляции длительности обычно нет вовсе. Отменённые вручную задачи не проверяются - там файл обрезан намеренно, и "Отменено" честнее. И вся проверка идёт под `timeout`: она сидит внутри запроса `?jobs`, а ffprobe, задумавшийся над файлом, который прямо сейчас дописывает ремукс, утаскивал за собой весь опрос - сайт отвечал "Не удалось обновить данные". Выход по таймауту вердикта не выносит вовсе: объявить файл битым по таймауту хуже, чем не проверить его.

### process_queue() - продвижение очереди

Очередь хранится в одном файле `dl_queue`, где каждая строка - это одна ожидающая загрузка. Метод открывает файл, ставит эксклюзивную блокировку (`LOCK_EX`), читает все строки, и для тех, на кого хватает места по лимиту `max_dl`, запускает реальную загрузку. Остальные строки остаются в файле. Блокировка нужна, чтобы два параллельных запроса (например, два человека одновременно открыли сайт) не испортили файл очереди друг другу.

### kill_one_of_them() и kill_them_all()

Останавливают один или все процессы yt-dlp. Важная деталь: перед тем как слать `kill`, метод проверяет через `/proc/$pid/cmdline`, что это действительно процесс yt-dlp, а не случайно совпавший по номеру чужой процесс на сервере. `kill_them_all()` ищет все процессы по имени (`pgrep -f 'yt-dlp'`) и завершает их, а также удаляет недокачанные `.part`-файлы, если в конфиге не включено `keepPartialFiles`. Записи трансляций до этой уборки не доживают: их `.part` уже переименован в нормальный файл (см. [Трансляции](#трансляции-прогресс-записи-и-спасение-оборванного-файла)).

Сигналы идут по нарастающей, и первым - **SIGINT**, а не SIGTERM. Именно его правильно обрабатывают и yt-dlp, и ffmpeg: дописывают заголовки, закрывают файл, выходят. Поэтому остановленная запись эфира остаётся нормальным играющим файлом, а не огрызком, который потом приходится спасать. Если процесс не ушёл, дальше идут SIGTERM и, в самом конце, SIGKILL. Одиночный "Стоп" ждёт ухода до двух секунд, "Стоп всё" - по 0.4 секунды на процесс: он обходит их много.

Сигнал шлётся не одному PID, а всей его группе процессов (`kill -- -$pid`, а не `kill $pid`). Каждая загрузка запускается через `setsid`, что делает её лидером собственной группы - для обычной загрузки (один процесс) это ничего не меняет, но для задач с переводом озвучки (VOT, `bash -c "yt-dlp & ... vot-cli & ... wait"`) без этого сигнал долетал бы только до внешнего `bash`, а `yt-dlp`/`vot-cli`/`ffmpeg`-микс оставались бы жить осиротевшими и после нажатия "Стоп". Подробнее - в [Очереди и других технических решениях](04-ochered-i-fishki.md#остановка-перевода-озвучки-целиком-а-не-только-внешнего-процесса).

### restart_download()

Перезапускает старую загрузку, читая сохранённую команду прямо из лога. Здесь есть отдельная проверка безопасности: команда из лога сверяется с ожидаемым путём к `yt-dlp` - если не совпадает, рестарт отменяется, чтобы подменённый лог-файл не заставил сервер выполнить чужую команду. Опциональные `$forceUseProxy`/`$forceUseCookies`/`$forceAltClient` используются авторетреями (см. ниже).

### Три авторетрея: прокси, куки и другой клиент

Когда задача завершается с ошибкой, `get_current_background_jobs()` пробует три независимых механизма авто-перезапуска - в этом порядке:

| | Сетевой (`autoRetryIfNeeded`) | Кукисный (`autoRetryWithCookiesIfNeeded`) | Клиентский (`autoRetryWithAltClientIfNeeded`) |
|---|---|---|---|
| Когда срабатывает | `isRetryableError()`: тайм-аут, 429, 503, DNS | `needsCookiesRetry()`: приватное видео, 18+, members-only, непробитый бот-чек | `unable to download video data` + `HTTP Error 403` на ссылке YouTube |
| Что подключает | SOCKS5-прокси (`restart_download(..., $forceUseProxy)`) | Куки (`restart_download(..., $forceUseCookies)`) | Другой клиент YouTube - `web_embedded`, без GVS PO-токена вовсе |
| Логика | Сайт блокирует прямые подключения, но пропускает через прокси | Ошибку чинит не сеть, а залогиненная сессия | CDN отбил ссылку, привязанную к PO-токену конкретного клиента (yt-dlp issues #16144, #14421). Повтор той же команды тут бесполезен и раньше зацикливался |

Общие правила для всех трёх: маркер `[RETRY_ATTEMPTED:]` в логе один на всех - за жизнь задачи максимум одна авто-попытка; для пользователя всё прозрачно - удался ретрей, видишь готовый файл, упали оба захода - финальную ошибку.

Сам перезапущенный процесс несёт метку `YTDL_AUTORETRIED` в переменных окружения команды - её проверяют все три детектора, чтобы не повторить попытку ещё раз, если уже перезапущенная задача упадёт снова. Метка пишется через `escapeshellarg()` (`YTDL_AUTORETRIED='1'` на Linux), поэтому детекторы ищут её без `=1` на конце - иначе кавычка сразу после `=` рвёт совпадение, гвард молчит всегда, и задача ретраится на каждом новом провале заново, накапливая противоречащие друг другу флаги. Конкретно так `--cookies` от одного ретрея и `--extractor-args youtube:player_client=android_vr` от другого однажды оказались в одной команде разом - `android_vr` кук не поддерживает, yt-dlp отказался от единственного заданного клиента целиком и не смог извлечь вообще ничего.

Сам рестарт **отложен на 10 секунд** (`RETRY_SCHEDULE_DELAY`). Метод обнаружения только дописывает маркер в лог, а запускает повтор `processScheduledRetries()`, которую `index.php` дёргает на каждом опросе рядом с `process_queue()`. Задержка нужна человеку: без неё новая задача перебивала бы своим прогрессом статус, который пользователь не успел прочитать ("Пробую другим клиентом YouTube", "Пробую через прокси", "Пробую с куками аккаунта"). Свободный слот (`canSpawnRetry()`) проверяет именно отложенный старт, а не постановка маркера: при `max_dl = 1` слот в момент падения почти всегда занят соседним роликом того же плейлиста, и плейлист не получал повторной попытки никогда. Не хватило слота - попробуем на следующем опросе, старый лог удаляется только после удачного старта.

Все три пути дополнительно упираются в `jobProducedFile()`: если задача всё-таки оставила файл в папке загрузок, повтора не будет. Без этой проверки удачная загрузка, в логе которой мелькнул пережитый самим yt-dlp 503 или тайм-аут фрагмента, скачивалась второй раз через прокси. Имя файла берётся не только из строк `Destination:`, но и из строки склейки форматов - у собранного из двух дорожек видео итоговое имя появляется только там.

Итоговым считается не любой `Destination:`. Видео и звук yt-dlp качает по отдельности и пишет их в `<имя>.f137.mp4` и `<имя>.f140.m4a`; после склейки удаляет сам. Если второе плечо отбили 403-м (обычное дело на бот-детекте YouTube), первое остаётся на диске законченным файлом - и раньше сходило за результат: задача показывалась "Готово", все три авторетрея молчали, а во вкладке "Видео" появлялся немой обрубок. Теперь такие имена разбираются отдельным списком (`collectLogTargets()`), успех по ним не засчитывается, а у провалившейся задачи `cleanupPartialFiles()` их удаляет. `FileHandler::listMedia()` прячет их из списков тем же шаблоном - на случай `keepPartialFiles`.

Кукисный ретрей дополнительно требует, чтобы куки были реально настроены и безопасны: `cookiesFileUsable()` проверяет, что файл существует, читается и не открыт группе/остальным (права чинятся до 0600 автоматически, если процесс - владелец). Если куки прописаны, но использовать их нельзя, `cookiesConfiguredButUnusable()` честно сообщает об этом в статусе задачи. Первая попытка всегда идёт без кук - публичный контент их вообще не видит. Как получить куки - в [Обходе бот-чека YouTube через куки](../how-to/05-obhod-bot-cheka.md).

## class/FileHandler.php - работа с файлами

Этот класс знает только про файлы на диске - он не запускает yt-dlp и не лезет в процессы.

- `listMedia()` - один проход `readdir()` по папке загрузок, который сразу возвращает и видео, и музыку (`['videos' => [...], 'musics' => [...]]`), каждый файл с возрастом в минутах и процентом "оставшегося времени жизни" (окно берётся из конфига `retentionMinutes`). Оба списка отсортированы по времени изменения, свежие сверху.
- `keepMarkerPath()`/`setPinned()` - закрепление файла ("пин") маркером `{имя}.keep` рядом с файлом, с тем же `realpath()`-предохранителем от выхода за пределы папки, что и у `delete()`. Закреплённый файл не участвует в возрастном отсчёте времени жизни - подробнее в [Закреплении файлов](04-ochered-i-fishki.md#закрепление-файлов-пин).
- `delete()` - удаляет один файл по имени. Здесь стоит защита от выхода за пределы папки: имя файла сначала чистится через `basename()` (убирает любые `../`), а затем через `realpath()` проверяется, что итоговый абсолютный путь действительно находится внутри разрешённой папки загрузок.
- `deleteAll()` - массовое удаление для кнопки "Очистить всё" (отдельно по видео/музыке или разом), с тем же `realpath()`-предохранителем; пропускает закреплённые файлы и, пока есть хоть одна работающая загрузка, файлы младше 60 секунд - подробнее в [Массовой очистке](04-ochered-i-fishki.md#массовая-очистка-отдельно-по-видео-и-музыке).
- `to_human_filesize()` - превращает байты в читаемый размер (КБ, МБ, ГБ).

## class/ProxyStatus.php - живость прокси

Небольшой класс, который отвечает за индикатор состояния SOCKS5-прокси в футере. Раз в минуту (`maybe_check()`, под неблокирующим flock, чтобы параллельные запросы не плодили процессы) он в фоне дёргает через прокси нейтральный `gstatic.com/generate_204` и дописывает в `tmp/proxy_probe.log` одну строку `timestamp 0|1`. По этой истории `get_windows()` строит три окна - 1, 5 и 15 минут - и отдаёт их в `?jobs`, откуда фронтенд красит точки в футере.

Сам прокси наружу не утекает: в лог идут только время и статус, строка прокси живёт лишь в окружении временного curl-процесса. Что видит пользователь и как читаются цвета - в [Очереди и других технических решениях](04-ochered-i-fishki.md#индикатор-живости-прокси-в-футере).

## class/PlaylistProbe.php - содержимое плейлиста

Структурно это копия `ProxyStatus`: неблокирующий `flock`, фоновый процесс, ответ запроса не задерживается никогда. Синхронно тут нельзя в принципе - `--flat-playlist -J` по SOCKS5 на большом списке идёт десятками секунд, а nginx обрывает ответ PHP на тридцатой.

`start($url, $ip)` либо отдаёт готовый результат из кэша, либо поднимает процесс и возвращает ключ; `read($key)` отвечает состоянием. Маршрутизацию (через прокси или напрямую, какие куки) и проверку ссылки класс берёт у `Downloader` - копий этих правил нет, проба обязана ходить туда же и так же, как пойдёт загрузка.

Ограничители: `flock` на ключ (две вкладки не поднимут две пробы), 5 запусков в минуту с адреса, 3 разбора одновременно, отказ при живом кулдауне хоста и при мёртвом прокси. Кэш живёт 10 минут, из ответа читается не больше 300 записей.

Вопрос "плейлист ли это" решает не разбор ссылки, а поле `_type` в ответе yt-dlp. Эвристика на фронте решает только одно - перехватывать отправку или нет; истину даёт сам загрузчик.

Ссылки записей собирает сервер. Часть экстракторов в плоском списке отдаёт голый идентификатор вместо адреса, и правила его достройки живут в одном месте, а не в двух.

В окно едут не все записи. Отбрасываются пустышки (`null` на месте удалённого ролика), записи без пригодной ссылки, недоступные (приватные, только для подписчиков, ещё не начавшийся эфир - и по приметам в заголовке, и по честному полю `availability`) и повторы одного ролика по `id`. Сколько отброшено, едет отдельным полем `hidden`; номер позиции в плейлисте (`position`) считается **до** отбрасывания, иначе нумерация в окне разъезжается с сайтом.

## class/Feedback.php - доска обратной связи

Хранилище без базы данных, как и всё остальное: один диалог - один JSON-файл. Номера выдаёт счётчик под эксклюзивной блокировкой (файл открывается на чтение-запись, а не на перезапись: перезапись обрезала бы его **до** взятия блокировки, и параллельный запрос прочитал бы пустоту). Запись всегда атомарная - временный файл рядом плюс переименование.

Каталог лежит выше корня сайта - отдать его по HTTP нельзя в принципе, правило `deny` в nginx только второй слой. Возрастная чистка сюда не ходит: в отличие от логов задач, отзывы вечны.

Об отправителе класс знает только HMAC от его адреса с локальным секретом. Голый хеш IP тут не годится - всё пространство IPv4 перебирается по нему за секунды. Ни адрес, ни User-Agent, ни куки в файл диалога не попадают вовсе.

Значок в подвале питает готовое число из `stats.json`, а не обход каталога: подвал рисуется на **каждой** странице.

**Права администратора** - две двери, обе узкие. Первая: адрес входит в список доверенных сетей (CIDR разбирается побитово, поэтому IPv4 и IPv6 обрабатываются одним кодом, а семейства не путаются). Вторая: пароль, причём он требуется на **каждое** действие - метки в сессии нет намеренно, иначе угнанная кука давала бы права до конца окна. Текст отказа одинаков для "пароль неверный" и "пароль не настроен": какая из дверей существует, снаружи знать незачем.

Права проверяются ровно один раз на запрос: `index.php` спрашивает разрешение и дальше передаёт готовый ответ в методы записи. Это не ради краткости - проверка двигает счётчик неудачных попыток, и повторный вызов внутри каждого метода списывал бы за одну опечатку две попытки из пяти.

С администратора сняты все ограничения, кроме физических: лимиты частоты, минимальная задержка, приманка, потолки длины и количества на него не действуют. Проверка свободного места остаётся - это не право, а физика.

Удаление сообщения перенумеровывает оставшиеся подряд: дырок в нумерации не остаётся ценой того, что старая ссылка на `#3` после удаления `#2` указывает на соседа. Удаление всего обращения счётчик номеров **не откатывает** - номера публичные, и переиспользование освободившегося увело бы старую ссылку на чужое обращение.

## class/Markdown.php - разметка сообщений

Защита здесь в порядке операций, а не в списке фильтров: **сначала** экранируется весь ввод, **потом** разбирается уже экранированный текст. Сырой HTML при этом невозможен по построению, поэтому отдельных запретов на `script`, `iframe` и прочее нет - этим тегам просто неоткуда взяться.

Разбор построчный. Одна регулярка через весь текст на 10 КБ способна выбить лимит возвратов PCRE, и тогда замена вернёт `null` - наивный код записал бы этот `null` и показал пустое сообщение. Поэтому результат каждой замены проверяется, а отказ откатывает рендер на простой блок текста.

Ссылки - единственное место, где пользовательская строка попадает в атрибут. Адрес проверяется **после** раскрытия HTML-сущностей (иначе `java&#115;cript:` проскочил бы) и после вырезания пробельных и управляющих символов; пропускается строго `http://` и `https://`, остальное рисуется текстом. Картинок нет намеренно.

## error_pages.php

Содержит одну функцию `showCsrfErrorPage()` - красивую страницу с кодом 403, которая показывается, если проверка CSRF-токена не прошла (например, страница была открыта слишком давно и токен в сессии устарел). Её кнопки ("Обновить", "Назад") работают через небольшой nonce-скрипт, а не через inline `onclick` - чтобы страница вписывалась в общую CSP без `unsafe-inline`.
